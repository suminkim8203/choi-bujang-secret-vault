# XDR-01 구현과 연결 상태

2026-10-07 로컬 작업 기록입니다. 보너스 실제 심판 판정은 아직 없습니다.

## 구현된 부분

1. 원본 경보28건에서 지정 다섯 항목을 읽습니다. 원본 파일과 공식 실행기는 보존합니다.
2. 반복 실패·같은 비밀번호의 여러 계정 대입·계정 변경 실패 폭주·비밀번호 후보 변경의 네 패턴을 적용합니다. 수치 기준은 실습용 정책이며 MITRE나 공식 채점 기준이 아닙니다.
3. `decide(alert)`는 패턴 증거가 명확하면 차단 후보, 정상 동작이면 기록, 나머지는 Jev 평가 대상으로 분기합니다. 기본 실행에서는 Jev가 비활성이라 알림으로 남습니다. 누락·가림·충돌 증거도 알림입니다.
4. `result.json`은 공식 실행기로 만들었습니다. 차단7·알림12·기록9입니다. 원본 설명을 직접 검토한 정상9건의 차단은0건입니다. 정상 분류 참고 목록은 자체 검토이며 공개 심판 정답표가 아닙니다.
5. `xdr:connect`는 차단 후보만 `deny-rules.json`으로 내보내고, 알림/차단 후보를 `xdr/alerts.log`에 중복 없이 기록합니다. 비밀번호·토큰·계정·경보 원문은 기록하지 않습니다. 다른 모듈의 로그는 유지합니다.
6. 차단 규칙은 근거 경보 ID·문서용 출발 주소·발생 시각·만료 시각을 갖습니다. 만료는 발생 시각에서15분 뒤입니다. 9월27일 시험 경보를 오늘의 실시간 차단으로 재활성화하지 않습니다. 현재 활성 규칙은0개입니다.

재현:

```sh
XDR_JEV_ENABLED=false npm run xdr:run -- brute-force
npm run xdr:connect
npm run test:xdr
```

정상 결과는 분류 합계28건, 검토한 정상 경보의 차단0건, 차단 규칙7개 내보내기입니다. 반복 연결 실행에서는 새 로그 줄이0개여야 합니다. 누락된 시간 범위를 경보 시각 하나에서 추정하거나, 여러 계정이라는 사실만으로 동일 비밀번호를 추정하지 않습니다. 고빈도 경보 중 증거가 부족한 경우도 알림에 포함됩니다.

## Jev: 구현됐지만 실제 연결은 미완료

`jev-client.mjs`는 [TypeSafe 공식 API](https://docs.typesafe.ai/api)의 요청/응답 형식을 사용합니다. 실제 호출은 `XDR_JEV_ENABLED=true`와 서버 환경의 `TYPESAFE_API_KEY`가 모두 있어야 합니다. 이번 작업에서 비밀키를 요구하거나 열지 않았고, 실서비스 호출·결제는 하지 않았습니다. 필요할 때 사용자가 공식 비밀 입력란에서 설정해야 합니다. 사용자 요청에 따라 비용/계정 준비는 뒤로 미룹니다.

질문은 Noul의 공격 여부입니다. 그 응답 `noul`은 공격일 가능성이며 Choice의 `confidence`와 다른 값입니다. `decide` 반환의 `confidence`에는 이 공격 가능성을 담고0.85/0.5 경계로 행동을 나눕니다. 고정 규칙의0.95, 정상0.05, 미응답0.5는 정책 값이며 모델이 측정한 확신도가 아닙니다. 합성 응답으로 경계·오류·시간 초과를 검사했고 실제 Jev 품질은 아직 검증하지 않았습니다.

모델에는 파생한 숫자·불리언 신호만 전달하도록 했습니다. 출발 주소·계정·시각·ID·경보 설명 원문·비밀값은 전송하지 않습니다. 응답 오류 본문과 예외를 로그에 넣지 않습니다. 이 정규화는 공식 가상 경보의 한국어 설명과 `data.srcip/srcuser` 집계 문맥에 맞춘 구현입니다. 실제 Wazuh 수집기의 집계 의미·원천 검증이 완료됐다고 주장하지 않습니다.

## ZTNA: 어댑터 검증 완료, 운영 연결 미완료

`ztna-gate.mjs`의 `withXdrGate`는 기존 판정기 앞의 추가 확인 부품입니다. 기존 deny/step_up은 유지하며, allow인 요청만 검증된 출발 주소의 아직 유효한 거부 규칙과 대조합니다. 기존 요청이나 규칙을 고치지 않습니다.

**현재 실제 `src/decider.mjs`는 모든 요청을 거부하는 원본 시작점입니다.** 테스트의 정상 통과는 별도로 만든 가상 allow 기준에 대한 어댑터 시험이며, 실제 판정기나 반 엔진에서 정상 통과를 확인한 것이 아닙니다. 실제 시작점의 거부가 보존되는 것도 검사했습니다.

2026-10-07 [공식 최신 요청 계약](https://github.com/ChoiTimo/aleph-defense-starter/blob/main/docs/DECIDER_REQUEST.md)을 다시 조회했고 로컬 문서와 Git blob SHA `9449cd7674c2d0ffa236c29bd13518fe08cb745f`가 같았습니다. 요청의18개 항목에는 출발 IP가 없습니다. `signals.source`는 출처 종류이며 IP가 아닙니다. `subjectId`도 Supabase 계정 ID와 직접 비교할 수 없습니다. 새로운 reasonCode는 운영 등록부에 등록돼 있어야 합니다.

따라서 운영 연결에는 다음 외부 정보가 필요합니다.

- 반 엔진이 검증한 출발 주소 또는 경보와 접속 주체를 연결하는 공식 매핑을 제공하는 위치.
- XDR 거부 사유/규칙을 운영 등록부에 등록하는 공식 절차.
- 정상 요청을 허용할 수 있는 기존 ZTNA 규칙의 준비 상태.

어댑터는 엔진 측 검증 주소 콜백과 등록된 거부 응답 콜백을 명시적으로 요구합니다. 브라우저가 입력한 주소를 믿거나18개 항목에 임의 필드를 덧붙이지 않습니다. 현재 이 어댑터를 호출하는 운영 경로는 없고, 실제 접속 차단·반 엔진 설치·심판 통과는 미확인입니다. 일반6단계를 임의 구현하거나 시작점의 거부를 허용으로 바꾸지 않았습니다.
