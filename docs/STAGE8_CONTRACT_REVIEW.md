## 가장 유력한 구현 한계와 미확인 사항

일반 UUID 메모 요청은 판정기에서 가명 사용자에 따라 소유권을 구별하지 못합니다. 현재 코드에서 확인되는 기능 누락이며, ‘최종 API도 검사한다’는 이유로 판정기 요구를 충족했다고 할 수 없습니다. 다만 이것이 실제 실패 입력의 직접 원인이라는 증거는 아직 없습니다.

공식 계약에는 subjectId가 발급자·대상·반·프로젝트를 묶은 가명이라고 명시돼 있고 Supabase 사용자 번호와 직접 비교하지 말라고 합니다. 자료 소유자·강사 역할·가명과 자료의 매핑 방법은 제공되지 않습니다. 검증되지 않은 사용자·기기·소유자 상수를 임의로 만들면 정상 권한 근거가 되지 않습니다. 전체 거부로 정상 요청까지 막는 방식도 요구를 만족하지 않습니다.

새 reasonCode의 운영 등록 상태와 심판이 판정기·실제 API·정적 코드를 어떤 방식으로 함께 검사하는지도 미확인입니다. 반복36점만으로 운영 오류나 캐시를 단정하지 않습니다. 현재 가장 정보 가치가 높은 확인은 **실패한 다른 구역 메모 조회 요청과 정상 요청의 공식 가상 예시를 받는 것**입니다.

## 강사·운영자에게 확인할 질문

> 8단계에서 최신 제출 bea80955c3b5는36점, 조건5개 중 ‘구역 규칙’ 실패와 S08_OTHER_ZONE_ALLOWED가 표시됩니다. 수정·목록·공지 수정은 격파로 표시되고, 실제 서버 API는 저장된 소유자 조건을 검사합니다. 공개 DECIDER_REQUEST v1의18항목에는 자료 소유자나 강사 역할이 없고 subjectId는 Supabase 사용자 번호와 비교하지 말라고 돼 있습니다.
>
> 1. 실패한 ‘다른 구역 메모 조회’와 정상 ‘자기 메모 조회’의 비밀값 없는 가상 요청 예시를 받을 수 있을까요? 특히 subjectId, deviceId, service, method, path, route를 확인하고 싶습니다.
> 2. 판정기에서 가명 subjectId와 자료 ID의 소유 관계를 어떤 검증된 설정 또는 계약으로 연결해야 합니까? 강사 역할은 어디에서 전달됩니까?
> 3. 이 실패는 decide 함수의 결과, 실제 API 응답, 코드 검사 중 어느 검사에서 발생했습니까? 기대 decision/reasonCode와 허용 이유 코드 목록도 확인 부탁드립니다.

이 질문을 대신 전송하지 않았습니다. 사용자에게 제공되는 문의 초안입니다. 추가 안내는 받지 않았다고 사용자가 확인했습니다. 9~12단계는 현재 잠겨 있으므로 시작하지 않았으며, 이후 XDR 변경도 하지 않았습니다.
